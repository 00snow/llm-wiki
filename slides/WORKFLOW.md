# 用 LLM Wiki 產生教學簡報：流程設計與反思

> 簡報：[`slides/index.html`](index.html)　·　知識庫：[`wiki/`](../wiki/index.md)　·　每一輪的檢查紀錄：[`build/check_report.md`](build/check_report.md)

## 步驟一：LLM Wiki（知識庫）

- **主題**：深度學習入門（什麼是 AI、神經網路、損失函數、最佳化、反向傳播、卷積、CNN）
- **先討論、後生成**：先和 AI 討論主題範圍（「資料放 NN、CNN、什麼是卷積、loss function、optimization」）、讀者是誰（第一次接觸 AI 的人）、
  頁面要長什麼樣子（比喻 → 原理 → 動手算），把這些寫成 `AGENTS.md` 的規則，**之後才**讓 AI 依規則收錄資料、寫頁面。
- **收錄了 8 份資料**（`raw/`）：維基百科（人工智慧、卷積）、Google 機器學習速成課程（神經網路、損失、梯度下降）、
  Stanford CS231n（反向傳播、CNN）、Karpathy 的 LLM Wiki 構想。每份都有來源頁，`wiki/log.md` 記了每一次 ingest。

## 步驟二：教學 HTML 簡報

`slides/index.html`，25 張教學投影片＋3 張幕後說明。每張下方都有「來源」標籤，點下去會打開它根據的 Wiki 頁。
鍵盤 ← → 換頁、N 開講者備註、T 切換深淺色；手機會自動改成往下捲的卡片。

## 步驟三：Loop / Graph 設計

![流程圖](graph.svg)

| 節點 | 誰做 | 輸入 → 輸出 |
|---|---|---|
| **A 取得資料** | 人挑來源，AI 剪輯 | 網頁 → `raw/*.md`、`wiki/` 頁面（依 `AGENTS.md` 7.1） |
| **B 查詢 Wiki** | `pipeline/query_wiki.py` | `wiki/` → `build/context.md`（給 LLM 的資料包）＋ `context.json`（給檢查用：每頁的數字、術語表、待查證清單） |
| **C 整理重點** | **LLM**（唯一的 LLM 節點） | 資料包 → `outline.json`（每張投影片的文字、算式、用哪張圖、來源 slug、負責解釋哪些術語） |
| **D 內容檢查** | `pipeline/check_outline.py` | 大綱 → 錯誤清單，每條錯誤寫明要退回哪個節點 |
| **E 產生簡報** | `pipeline/build_slides.py` | 大綱＋`wiki/diagrams/*.svg` → `index.html` |
| **F 版面檢查** | 瀏覽器（`__checkLayout()`）＋逐張截圖 | 桌機 1280×760、手機 375 寬，檢查超出版面、橫向捲動、圖文是否相符 |

**D 會檢查的東西**

| 代碼 | 檢查 | 不通過退回 |
|---|---|---|
| SOURCE | 每張都要標來源，而且 slug 存在 | C |
| NUMBER | 投影片（含講者備註）的每個數字，都要出現在它引用的 Wiki 頁 | C；Wiki 本身沒有 → A |
| UNVERIFIED | 不可以用 Wiki 標「待查證」的內容（目前是「交叉熵」） | **A**：先收錄來源，再重跑 B |
| MATH | 算式真的算一次，`=` 兩邊要相等 | C |
| JARGON | 術語要先解釋（`defines`）才能在後面使用 | C |
| LENGTH | 字數、條數上限（給初學者看，一張不能太擠） | C |
| DIAGRAM / QUIZ | 圖檔存在；測驗答案在選項裡 | C |
| MISMATCH（v2 新增） | 算式的數字要出現在「這張圖在 Wiki 裡所在的那一段」 | C |

**哪些步驟會重複？**
- **C ⇄ D** 是主要的迴圈：D 每次都整份重新檢查，但 C **只重寫錯的那幾張**，最多 3 輪，還錯就停下來問人。
- **E → F** 每次產生後都要跑；F 發現的問題分兩種：**樣式**（字太小、留白怪）→ 改 `template.html` 重跑 E；**內容**（圖文不符）→ 退回 C，再過一次 D。
- **A → B** 只有缺資料時才會跑（UNVERIFIED，或 NUMBER 錯誤是因為 Wiki 本來就沒有這個數字）。

**為什麼這樣設計？**
1. **只有 C 交給 LLM，其他都是腳本。** LLM 擅長改寫、比喻；不擅長數字數、算算術、記得術語順序。這些交給程式檢查，結果是確定的、可以重跑。
2. **檢查要能「指路」。** 每個錯誤碼都對應一個退回節點，所以知道該重寫一張投影片、還是該回去找資料。
3. **事實只有一條來路**：raw → wiki → 簡報。D 的 NUMBER 檢查保證簡報不會出現 Wiki 沒有的數字，Wiki 自己的規則又保證數字追得回 raw。
4. **局部重寫**：只改錯的那幾張，已經通過的不會被 LLM 改壞。

## 步驟四：反思（實際執行一次之後）

實際紀錄在 [`build/check_report.md`](build/check_report.md)，以下是重點：

| 輪 | 發生什麼事 |
|---|---|
| 1 | 第一版大綱 24 張，**16 個錯誤**（JARGON 11、LENGTH 5）。其中 13 個是**檢查器誤報**：封面和路線圖這種預告頁只是列出名字，不算「使用」術語（11 個）；路線圖的條數上限和 slug 被算進字數（2 個） |
| 2 | 修檢查器（`preview` 頁豁免、slug 不算字數）後剩 **5 個真錯誤**：3 張字數超標、2 張術語先用後教（「一層包一層」用了「神經網路」、激勵函數頁用了「梯度消失」）|
| 3 | 只重寫那 5 處 → 0 錯誤 |
| F | 截圖發現 3 個 D 抓不到的問題：①網址改 `#7` 不會換頁（模板 bug）②講解圖太小、「一層包一層」最內層是空的大框（樣式）③**第 21 張把最大池化的圖，配上卷積輸出大小的算式**——數字、算式都對，但聽眾會以為在算池化 |
| 4 | ③ 退回 C，拆成兩張 → 0 錯誤 |
| 5 | 用 v2 規則（限制已寫進資料包）寫最後 3 張幕後投影片 → **第一次就 0 錯誤** |
| 6 | 截圖發現流程圖太小看不清，只改版面欄位（`fig: wide`）→ 0 錯誤 |

**1. 哪一個節點最常出錯？**
**C（整理重點，LLM 節點）**。真正的內容錯誤全部來自 C：字數超標（LLM 很難準確數中文字數）、術語先用後教（寫的時候會順手預告後面的詞）、把兩個例子塞進同一頁。
第二名其實是 **D 自己**：第一輪 16 個錯誤裡有 13 個是誤報，檢查器也需要被檢查。

**2. 發現問題後，把檢查往前移到哪一步？**
- **移到 B（查詢 Wiki）**：原本字數上限和術語規則只寫在 D 裡，C 寫的時候看不到。現在 `rules.json` 升到 v2，B 產生資料包時把「字數上限、術語要先 defines、一張只講一個例子」放在最上面，C 一開始就照著寫，而不是寫完才被退回。
- **從 F 移到 D**：圖文不符原本只有看截圖才發現。現在 D 多了 MISMATCH：找出那張圖在 Wiki 裡所在的段落，算式的數字至少 80% 要出現在那一段。用第 21 張的舊版測試：只有 29%，會被擋下；其他 5 張動手算都是 100%。
  （第一版是拿 SVG 裡的數字比對，結果舊版第 21 張有 86% 對得上——池化圖裡全是 0～9 的小數字——抓不到，所以改成比對 Wiki 段落。）

**3. 有沒有因此修改 workflow / graph？為什麼？**
有，改了三個地方：
1. **B 多了一個輸入 `rules.json`**（圖上的奶油色方塊）：預防比退回便宜，每退回一次 C 就要多一輪。
2. **D 多了 MISMATCH**：能用程式檢查的就不要留到最後靠人眼。
3. **F 的退回分成兩條**：樣式 → 改模板重跑 E；內容 → 回 C 再過 D。一開始 F 只有「回 E」，但第 21 張的問題改模板修不好，必須回 C 改大綱。

另外也修了檢查器本身（預告頁豁免），因為誤報會讓人開始忽略錯誤訊息。

**限制（老實說）**：這次 C 節點和寫檢查器的是同一個 AI，它本來就知道規則，所以第 5 輪「一次通過」的說服力有限。更嚴格的做法是讓 C 用一個只看得到 `context.md` 的獨立 LLM 來跑。
